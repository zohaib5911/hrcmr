### [ ] C4.2.1 · P1 · Stop server-rendered register pages sharing one visitor rate-limit bucket (from C4.1.1 / T20.4)
- **Problem:** `api/app/modules/register/public.py:47` `_limit_reads` keys every `/public/register/*` read on `client_ip(request)`, with 120 reads/minute. The public register pages fetch through `registerGet` in `web/lib/register.ts:26` from the Next.js server over `API_INTERNAL_URL`, and send no visitor address. In production the peer is the web service's Railway private address (trusted in `app/core/client_ip.py` `RAILWAY_PRIVATE_RANGES`) and there is no `X-Real-IP`, so `resolve_client_ip` returns the web server's own address. So every visitor and crawler shares one budget: more than 120 uncached profile, region, bulletin or sitemap renders in a minute (a search crawler walking the sitemap's sponsor profiles is enough) get 429. `registerGet` then throws and the public page fails with a server error for everyone.
- **Fix:** in `_limit_reads`, find internal server-to-server calls: the direct peer (`request.client.host`) is inside `trusted_proxy_networks(request.app.state.settings)` **and** the request has no `x-real-ip` header. Give those calls their own bucket, `READ_INTERNAL = ("public.register.read.internal", 6000, 60)`, keyed by the peer address. Keep the 120/minute per-visitor bucket for every other request, the explorer's own `_limit` and the report limit/Turnstile as they are. Don't forward visitor headers from `registerGet` (that would break the ISR fetch cache). Add a comment saying why.
- **Done when:** new tests in `api/tests/db/test_register_public.py` (copy the existing C4.1.1 limiter tests): (a) with `trusted_proxy_cidrs` covering the test peer and no `X-Real-IP`, 121 reads in a window all succeed; (b) the same trusted peer sending `X-Real-IP: <visitor>` still gets 429 after 120 for that visitor, and a second visitor is allowed; (c) an untrusted peer still gets 429 after 120. The existing register limiter/report tests, Ruff and mypy pass.

### [x] C4.2.2 · P2 · B · Keep the Companies House bulk index to the sponsors' names (from C4.1.15) — fixed in PR #108
- **Problem:** `api/app/modules/register/geo.py` `load_company_dataset` / `match_from_latest_dataset` stores the whole monthly bulk CSV (about 2.5 GB, roughly 450 MB gzipped) as one `bytea` row, and every changed import decompresses it, decodes it to one string and builds a dict of about 5M names in the worker. `app/cli.py` `load-companies` also reads the whole file into memory. When the flag is on, this risks a worker OOM or a failed import on a small instance (the runbook only warns about it).
- **Fix:** keep the behaviour (exact names, whole-file duplicate rejection, provenance, flag default off), but stream the CSV (`csv.reader` over `io.TextIOWrapper(gzip/file)`) and keep only the rows whose normalised name is a current or former register sponsor name, plus the names seen twice, so duplicates are still rejected. Store that reduced, compressed index as the dataset content instead of the raw file, and record the original SHA-256 as now. Update `docs/runbooks/register-companies.md`.
- **Done when:** the existing C4.1.15 tests pass unchanged, and a new test shows a name duplicated in the source file stays unmatched while the stored content holds only sponsor-relevant names.
